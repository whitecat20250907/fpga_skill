# v52–v53：眼控结束、标定恢复与锁定后动作修复

2026-10-26。已部署RK。没有改动FPGA位流、DMA、采集所有者、模型权重、应用内容或用户映射。

## 现场证据与根因

v52修复前，握拳确认先要求当前视线有效；无效帧会消耗握拳而保持POINTING。网页入口还可能把先出现在列表中的另一只手当作操作手。旧单人人脸编号残留会阻止重新标定。

用户已确认v52能握拳锁定。现场engine日志在单调时间74918301771360记录“已锁定 右心房”，74924310759322进入WRITING且仍为LOCKED；随后74928427208545开始的新引擎会话清空了内存状态，后续轨迹聚焦报“请先眼控接管并握拳锁定目标”。这一次实际中断对应本轮v52b部署重启，不是已证实的DMA崩溃。补丁部署打断了用户联测。

关联审查发现：单人丢脸会清掉冻结目标与待确认手势，点击执行端还要求实时标定；轨迹待确认即使关闭face_guard，仍比较旧单人槽位。这些均会破坏“眼控结束后只用手操作”的约定。

## 已落地行为

- 眼控阶段原操作手松开再握拳结束；网页入口由实际做出握拳的已准备手认领。允许唯一同侧手在短暂track变化后接续；另一侧不冒充原手。
- 结束眼控的握拳采用0.55置信度、0.22秒、至少3个新鲜帧。无有效目标也会结束本段眼控，但不制造锁定或点击。
- 锁定后冻结坐标、目标和锁定代号。单人丢脸、眼动服务重启或手部服务短暂健康中断，不再撤销冻结目标；新鲜手势恢复后可以操作它。手部异常期间不执行动作。
- 点击、游戏确认和医学聚焦按已有锁定与新手势确认执行，不再要求持续眼动输出或仍有效的标定。普通静态手势确认、轨迹另一只手确认保持原流程。
- 单人待确认轨迹不因人脸槽位清空取消。双人归属、模式切换、应用切换、急停、硬件epoch变化和重新标定的隔离仍保留。
- 单人旧人脸丢失会解除旧标定选择；新标定使用当前就绪人脸。完成/失败后的标定允许重新开始。冻结目标可继续操作，但再次眼控仍需要有效个人标定。
- HDMI显示操作手、松拳提示、握拳进度和锁定目标。锁定后显示“手势点击 / 聚焦；再次眼控接管才移动鼠标”。日志增加状态、锁定代号与健康信息。

引擎进程重启仍会结束内存交互会话，不能声称支持跨进程无损恢复；本轮最终重启已完成。实际目标消失/应用改变时点击仍会拒绝，不把旧目标当作新页面的按钮。医学聚焦保留对冻结坐标的操作语义。无限次“确认手张开再握拳重复上次指令”的全链路仍按历史待完成范围处理，本轮仅验证多次明确动作提交不丢锁。
